What the project is

WhichAI.dev is a picture gallery, not a scoreboard. One person, Dara Adedeji, gave the same short brief to 25 AI models: design the landing page for a note-taking app that works like a second brain, five separate attempts, each on its own page. He then rebuilt every generated app inside a single website so a visitor can look at them side by side.

Every page in the gallery is live code, not a screenshot. Click a card and you are running that model's actual Next.js output inside the gallery shell.

The prompt, stored as a plain string at src/app/page.tsx:21 and shown to visitors with a copy button, reads like dictation rather than a specification:

“I want you to design the landing page for a note-taking application as essentially a second brain. You should design five iterations and each of them should be accessible within the slash one, slash two, slash three like pages directory. And then you should add a little button that lets me switch between them easily.”

It sets no constraints at all: no brand, no colour, no content, no length. Every model invents the product name and the copy. That looseness is the point. The project measures what a model reaches for when nobody tells it anything, which is close to how most people actually prompt.

What the data model cannot hold

A run is described by eight fields, and none of them is a date. The gaps are not oversights in the writing, they are missing fields:

  • When the run happened. Nothing is date-stamped. The gallery spans March to August 2026 and two cards in one row can be five months apart.
  • Which agent ran it. Cursor, Claude Code, Codex and a raw API call all look identical here. Folder names hint (opus-cc-test) and hints are all you get.
  • The exact model build. “Opus 5” is a display label, not an API model string.
  • Reasoning effort, retries, and cost. One backup folder in git history shows at least one run was redone. Nothing marks it.
  • Any score. No rubric, no rater, no numeric field. That is a deliberate choice and a good one.

One more precision worth stating: the five iterations in each run are five different designs the model was asked to produce in one sitting, not five repeats of the same design. They measure range within one attempt. Nothing in the project measures run-to-run consistency.

The headline finding: skill version drift

The design-skill group is not one treatment. Eighteen of the 65 runs carry a lockfile recording the exact skill file installed for that run. Those lockfiles point at four different versions of Anthropic's frontend-design skill and two different versions of the taste skill.

What this costs, precisely

Comparing two cards across models inside the “With Design Skill” section compares two instruction files as well as two models. But the comparison the site is actually built around, one model with the skill against the same model without it, is not affected, because both halves of that pair were run together. That pairing is the site's strongest claim and it survives intact.

Two related findings:

  • One taste run had 13 skills installed, not one. The GLM 5.2 taste run's lockfile lists brandkit, gpt-taste, minimalist-ui, industrial-brutalist-ui, image-to-code and eight more. Every other taste run lists exactly one. That card's output cannot be attributed to the taste skill alone.
  • 47 of 65 runs record nothing. Their treatment is asserted by folder name. There is no reason to doubt the labels, but they are testimony rather than evidence.

Architecture: 325 hostile stylesheets in one document

The engineering problem is worth stating plainly. Each of the 65 runs arrived as a complete Next.js project with its own global stylesheet that sets the page background, its own @keyframes animations, and its own floating switcher pinned to the top-right corner. All of them now render inside one site with one shared navigation bar.

Think of it as mounting 325 paintings in one hall: every painting keeps its own frame and lighting, and none of them may repaint the walls.

The chain from data to pixels

gallery-manifest.ts  -->  gallery-registry.ts  -->  src/variants/{group}/{model}/index.tsx
   (the list)               (the lookup)                    (the adapter)
                                                                 |
                                                                 v
                                       the model's own page components, imported directly
                                                                 |
                                                                 v
                                    src/generated/scoped-variant-css/... (rewritten CSS)

One manifest is the single source of truth. A hand-maintained array of 65 entries. Every route, thumbnail, dropdown option, test case and guessing-game round derives from it. Nothing else holds a list of models.

The idea worth copying

A build script rewrites every variant stylesheet so its rules can only reach its own container. A rule written as .hero { } in the Opus 5 design-skill run becomes: 

:where(.gallery-generation[data-gallery-group="with-design-skill"][data-gallery-model="opus-5"]) .hero { }

The :where() wrapper is the clever part. It contributes zero specificity, so the model's own rule ordering survives untouched. Without it, every rule would gain the weight of three extra selectors and the original cascade would scramble.

Three more transformations in the same pass:

  • Page-level selectors become the scope itself. html, body and :root are replaced rather than prefixed, so a model's body { background: #0a0a0a } styles only its own container.
  • Animations get namespaced. @keyframes float becomes @keyframes gallery-with-design-skill-opus-5-...-float, with every animation declaration rewritten to match. Without this, two models that both named an animation float would silently overwrite each other.
  • The global Tailwind entry is stripped from each variant copy, because the shell sets Tailwind up once.

Stage two gives each run its own Tailwind bundle: a literal route folder per run whose four-line stylesheet switches off automatic file scanning and points at exactly one variant folder. So a visitor to one generation downloads only that generation's utility classes. Three of the 65 runs are missing theirs, which is finding E4.

The whole site is prerendered: 325 gallery pages plus 325 switcher-free preview pages, all static files. The compare page holds its full state in six URL parameters and renders two generations as iframes, which is the only way two apps with conflicting global styles can share a screen.

Fix order: E4 then E1 together, because either alone breaks something and together they are the biggest win for every visitor. Then E3, which is two lines and repairs the first thing anyone sees. Then E5, because legal exposure does not improve with age.

Where it sits among neighbours

Design Arena, DesignArena and the academic UI-Bench all produce scores, through crowd votes or automated rubrics. WhichAI.dev produces no score and hands you the artifacts instead. Its README states the position directly: other leaderboards prove “Model A is 2.3% better than Model B” and none of them answer “if I ask this thing to build a landing page, will it look good?”

Its distinctive asset is the corpus. 325 preserved, running, side-by-side generated applications from 25 models under labelled conditions appears to be unique. No leaderboard lets you open the code.

How to read this benchmark

QuestionDoes the site answer it?
What does this model produce from a blank brief?Yes, directly, five ways.
Does installing a design skill change that, for this model?Yes. Paired, one click, one shareable URL.
What visual tics does this model have?Yes, and the guessing game teaches you to spot them.
Which model is best at design?No. No score exists, and the one ranked list covers eight superseded models.
Is the design skill worth installing, in general?No. Four skill versions inside one group confound it.
How consistent is this model?No. Nothing repeats a run.
Did the model follow the brief?No. The switcher it asked for is deleted at ingestion.
When, with what agent, on which skill version?No. None of it is recorded.

Closing the last two gaps needs a data-model change of a few hours and one extra sweep. Neither requires a rubric, a crowd, or a scoring model, which means the project can fix them without becoming the kind of leaderboard its own product document says it must never become.

Evidence boundary: the local checkout at commit 3bdd0cb, the live site as served on 11 August 2026, and the GitHub API on the same day. The project was not built or run, no generated page was re-graded, and no model was re-run. Full method, confidence grades and sources are in the accompanying markdown view.

Criticism here is aimed at how the artifact should be read, not at the work. The architecture is genuinely good, the ingestion skill is genuinely reusable, and the decision not to invent a score is better judgement than most benchmarks show.
